# 记账App 漏洞修复 — 多角色协作计划

> 基于全项目代码审查结果（19严重/11高优先级/20+中低优先级），参照正规软件公司开发流程，设计以下协作架构。

---

## 一、团队角色与职责

| 角色 | 人数（模拟） | 核心职责 | 不做什么 |
|------|-------------|---------|---------|
| **PM / 需求分析师** | 1 | 基于审查报告制定修复优先级、验收标准、版本规划 | 不写代码 |
| **技术负责人 / 架构师** | 1 | 审核跨模块影响、定义接口契约、把控技术方案风险 | 不写业务代码 |
| **数据层工程师** | 1 | Room数据库、Migration、事务、Preferences、数据安全 | 不碰UI层 |
| **业务逻辑工程师** | 1 | AI调用、计划执行、自动采集链路、分类服务、日志脱敏 | 不碰Compose UI |
| **UI工程师** | 1 | ViewModel状态管理、Compose屏幕、生命周期、主线程调度 | 不碰数据库Migration |
| **QA / 测试工程师** | 1 | 设计测试用例、回归测试、边界测试、验收确认 | 不修复Bug |
| **DevOps / 工具链** | 1 | 编译检查、Lint、版本号管理、APK构建、分支管理 | 不写功能代码 |

---

## 二、协作流程（阶段划分）

```text
审查报告输入
    ↓
[阶段1] PM需求确认 → 输出《修复需求文档》+ 优先级 + 验收标准
    ↓
[阶段2] 架构师技术方案评审 → 输出《技术方案》+ 影响分析 + 接口契约
    ↓
[阶段3] 并行开发（3条线）
         ├── 数据层工程师：数据库事务 + Migration + 加密存储
         ├── 业务逻辑工程师：采集链路 + 计划执行 + AI调用 + 日志脱敏
         └── UI工程师：主线程调度 + ViewModel泄漏 + Compose状态
    ↓
[阶段4] 自测 + QA用例设计（并行）
    ↓
[阶段5] Code Review（交叉审核）
    ↓
[阶段6] 集成验证（全链路回归）
    ↓
[阶段7] DevOps检查（编译/Lint/版本号/APK）→ 合并主干
    ↓
[阶段8] 上线验收 + 监控
```

### 阶段2：架构师技术方案评审

**输入**：《修复需求文档 v1.0》 + 现有代码库
**输出**：《技术方案文档》+ 分支策略 + 接口变更清单

**架构师核心任务**：
1. **跨模块影响分析**：
   - `MainViewModel` 改 `Dispatchers.IO` 会影响所有 UI 状态的即时更新，需确认 `_uiState` 的更新都在主线程回抛
   - `PlanExecutor` 加事务会影响 `BillTransaction` 的异常传播，需确认 `ExecuteResult` 状态机兼容
   - `CategoryService` 改走 `PlanExecutor` 会新增异步接口，需确认调用方（UI层）已适配
2. **接口契约冻结**：
   - `PlanExecutor.execute()` 入参不变，但内部实现改为 `database.runInTransaction { }`
   - `AppRepository.executePlan()` 移除 `@Transaction`，改为调用 `planExecutor.execute()`
   - `UserPreferences` 新增 `setApiKeyEncrypted()` / `getApiKeyEncrypted()`，旧方法标记 `@Deprecated`
3. **分支策略定义**：
   ```
   main (保护分支)
    │
    ├── hotfix/p0-amount-precision      ← R-S1
    ├── hotfix/p0-main-thread-io        ← R-S2
    ├── hotfix/p0-node-recycle          ← R-S3
    ├── hotfix/p0-notification-crash    ← R-S4
    ├── hotfix/p0-transaction           ← R-S5
    ├── hotfix/p0-migration-safety      ← R-S6
    ├── fix/p1-callback-leak            ← R-S7
    ├── fix/p1-api-key-security         ← R-S8
    ├── fix/p1-log-sanitization         ← R-S9
    └── fix/p2-concurrent-safety        ← R-S14
   ```
4. **风险标记**：
   - 🔴 高风险：`MainViewModel` 调度器改动牵一发而动全身，需全链路回归
   - 🔴 高风险：数据库Migration改动一旦出错，用户数据永久丢失，必须在测试数据库上验证所有版本跳跃（1→6, 2→6, 3→6...）
   - 🟡 中风险：引入 `security-crypto` 会增加 APK 体积约 200KB，需确认接受

**评审通过标准**：所有 P0 需求有明确技术方案；无未解决的跨模块冲突；分支命名规范确认。

### 阶段5：Code Review（交叉审核）

### 阶段6：集成验证

**由 QA 主导，全体开发配合**

   - 1000条记录下Dashboard打开时间 < 1s
   - 连续采集100次通知，内存波动 < 10MB

## 四、沟通机制

### Daily Stand-up（每日站会，15分钟）

格式（每人回答3个问题）：
1. 昨天完成了什么？
2. 今天计划做什么？
3. 有什么阻塞需要协调？

### 阻塞升级路径

```
开发个人阻塞（如技术方案不确定）
    ↓ 15分钟无法解决
同组其他工程师协助
    ↓ 30分钟无法解决
技术负责人介入决策
    ↓ 涉及需求变更
PM确认优先级/裁剪需求
```

### 文档规范

- 所有技术决策必须记录在《技术方案文档》的 "Decision Log" 中
- 所有 Code Review 评论必须 Resolve 后才能合并
- 所有 Bug 修复必须关联需求ID（如 `Fixes R-S1`）
