**模块间调用规则**：
- UI 模块 → 数据库模块：通过 `AppRepository` 接口（只读查询 + 计划执行）
- UI 模块 → AI 模块：通过 `MainViewModel` 发起 AI 请求，不直接调用 Retrofit
- 数据采集模块 → 计划执行模块：通过 `CaptureDispatcher` 分发到 `MainViewModel`，最终落入 `PlanExecutor`
- AI 模块 → 计划执行模块：通过 `AiPlanner.parse()` 生成 `AiOutput`，经 `PlanBuilder` 转为 `BillExecutePlan`
- **禁止跨模块直接修改对方内部文件**

## 四、Definition of Done（完成标准）

任何 Issue 进入 **Done** 状态前，必须满足以下全部条件：

### 4.1 通用 DoD（所有优先级）

- [ ] **代码完成**：实现符合需求描述，无 TODO/临时代码
- [ ] **单元测试通过**：新增/修改的代码覆盖率 ≥ 80%
- [ ] **Lint 通过**：`./gradlew lint` 无 ERROR，WARNING 需有合理理由
- [ ] **CI 通过**：`assembleDebug` + `lint` + `testDebugUnitTest` + `detekt` 全部 green
- [ ] **Code Review 通过**：
  - P0 Issue：Tech Lead + 另一位模块负责人 **双 Approve**
  - P1/P2/P3 Issue：至少 1 人 Approve
- [ ] **无冲突**：与 `release` 主干无 merge conflict
- [ ] **日志规范**：新增关键路径包含 `AppLogger` 日志（requestId + node）
- [ ] **敏感信息检查**：代码/日志中无 API Key、用户隐私数据明文

### 4.2 P0 专属 DoD（额外要求）

- [ ] **QA 手工验证通过**：QA 按照《测试用例清单》执行，结果 PASS
- [ ] **边界测试通过**：金额为0、负数、超大数、空字符串等边界条件
- [ ] **回归测试通过**：核心流程（AI记账、手动记账、自动采集）无 regression
- [ ] **CHANGELOG 更新**：在 `CHANGELOG.md` 中记录修复内容
- [ ] **架构师确认**：Tech Lead 确认无跨模块副作用

### 4.3 数据库变更专属 DoD（ISSUE-005/006/010/011）

- [ ] **Migration 测试通过**：验证所有版本跳跃路径（1→6, 2→6, 3→6, 4→6, 5→6）
- [ ] **数据完整性验证**：升级前后数据条数一致，无静默丢失
- [ ] **降级策略确认**：若 Migration 失败，有明确的用户提示或回退方案

## 五、CI Gate（合并门禁）

### 5.1 CI 流水线流程

```text
开发者推送分支
        │
        ▼
创建 Pull Request
        │
        ▼
┌─────────────────┐
│   CI 自动触发    │
├─────────────────┤
│ 1. assembleDebug│  ← 编译必须通过
│ 2. lint         │  ← 无 ERROR
│ 3. unitTest     │  ← 全部单元测试通过
│ 4. detekt       │  ← 代码质量检查通过
└─────────────────┘
        │
    ┌───┴───┐
    ▼       ▼
Failed   Passed
    │       │
    ▼       ▼
阻断PR   进入Code Review
         （P0需双Approve）
                │
                ▼
            Merge到release
```

### 5.2 CI 失败阻断规则

| 检查项 | 失败后果 |
|--------|----------|
| `assembleDebug` 失败 | PR 自动标记 `blocked`，禁止合并 |
| `lint` ERROR | 同上 |
| `testDebugUnitTest` 失败 | 同上 |
| `detekt` 严重违规 | 同上 |
| CI 通过但 Review Rejected | 禁止合并，需修复后重新触发 CI |

### 5.3 CI 配置文件（建议新增）

文件：`app/.github/workflows/ci.yml`（或项目级 CI 配置）

```yaml
name: CI Gate
on:
  pull_request:
    branches: [release/*, main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Grant execute permission for gradlew
        run: chmod +x gradlew
      - name: Assemble Debug
        run: ./gradlew assembleDebug
      - name: Lint Check
        run: ./gradlew lint
      - name: Unit Tests
        run: ./gradlew testDebugUnitTest
      - name: Detekt
        run: ./gradlew detekt
```

> 注：当前项目尚未配置 CI，DevOps 模块负责人需先完成 CI 配置（ISSUE-SETUP-CI）。

## 六、Code Review 矩阵（v2 严格版）

### 6.1 审核矩阵

| Issue 优先级 | 审核者 1（必审） | 审核者 2（必审） | 关注重点 |
|-------------|----------------|----------------|---------|
| **P0** | Tech Lead | 另一位模块负责人 | 架构一致性、副作用、边界条件、测试覆盖 |
| **P1** | Tech Lead 或 协调者 | 任意模块负责人 | 代码规范、日志脱敏、异常处理 |
| **P2/P3** | 任意两位开发 | — | 代码风格、是否有更简单方案 |

### 6.2 Review Checklist（Reviewer 必须逐条勾选）

- [ ] 是否符合 Kotlin 官方风格指南
- [ ] 是否引入 `!!` 强制解包（零容忍）
- [ ] 是否使用 `GlobalScope`（零容忍）
- [ ] 新增关键路径是否包含 `AppLogger` 日志（requestId + node）
- [ ] 是否触碰了未要求修改的相邻代码（精准修改原则）
- [ ] 单元测试是否同步更新，且命名规范 `[方法]_[场景]_[预期]`
- [ ] 协程切换是否正确（`Dispatchers.IO` / `Dispatchers.Main`）
- [ ] 敏感信息是否脱敏（金额、商户、API Key、用户输入）
- [ ] 数据库操作是否有事务保护（如适用）
- [ ] 是否导致模块间接口契约变更（如变更需同步更新调用方）

### 6.3 Review 评论规范

```
[严重]  必须修改，否则不Approve
[建议]  最好修改，但不阻塞合并
[疑问]  需要作者澄清
[赞赏]  好的实践，值得推广
```

## 八、集成协调者（Integration Coordinator）工作流程

### 8.1 职责

- **不直接写代码**
- 将 Issue 指派给对应模块负责人
- 跟踪模块间依赖关系，确保上游模块先完成
- 每日汇总各 Agent 进度，识别阻塞
- 在合并前统一验证：
  - 模块间接口契约是否一致
  - 是否有文件被多个模块同时修改（冲突预警）
  - 版本号是否正确更新
  - CHANGELOG 是否同步

### 8.2 协调者每日站会输出格式

```markdown
## 2026-07-20 站会纪要

### 进度总览
| Issue ID | 模块 | 状态 | 负责人 | 阻塞 |
|----------|------|------|--------|------|
| ISSUE-001 | 数据采集 | In Progress | Agent-A | 无 |
| ISSUE-004 | UI | PR Opened | Agent-B | 等待CI |
| ISSUE-005 | 数据库 | Todo | Agent-C | 依赖ISSUE-010方案确认 |

### 今日风险
- ⚠️ ISSUE-004 的 `MainViewModel` 改动可能影响 ISSUE-005 的 `PlanExecutor` 调用方式
  - 措施：协调两位负责人确认接口契约

### 明日计划
- ISSUE-001 进入 Code Review
- ISSUE-005 开始开发
```

### 8.3 冲突预警机制

当两个模块的 PR 同时修改了同一文件时：

```text
冲突预警
├── 文件: MainViewModel.kt
├── 修改方:
│   ├── ISSUE-004 (UI模块) - 添加 withContext(Dispatchers.IO)
│   └── ISSUE-007 (UI模块) - 添加 onCleared() 清理
├── 决策: 同一模块内冲突，由模块负责人自行合并
└── 若跨模块冲突（如数据库模块和UI模块都改AppRepository.kt）：
    └── 协调者介入，要求双方重新划分修改范围
```
